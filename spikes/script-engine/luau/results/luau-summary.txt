MODULE FORMAT, SANDBOX, REMOVALS
  The module is `local M = {} function M.execute(ctx, input) ... end return M`. Run: lua.load(src).eval() gives M,
  then M.execute(ctx, input). ctx is an argument (not a global), a read-only table with notify, now, count, block_recv, try.
  Removed before sandbox(true): os, io, debug, package, require, load, loadstring, dofile, loadfile, collectgarbage,
  gcinfo, print, warn, getfenv, setfenv, newproxy, math.random, math.randomseed, string.dump (absent anyway).
  Plain Lua::new() has 39 globals. 10 of them are removed here: collectgarbage debug gcinfo getfenv loadstring
  newproxy os print require setfenv. 29 remain in the sandbox: _G _VERSION assert bit32 buffer coroutine error
  getmetatable ipairs math next pairs pcall rawequal rawget rawlen rawset select setmetatable string table tonumber
  tostring type typeof unpack utf8 vector xpcall. (io, load, loadfile, dofile, package, warn and string.dump are not
  in Luau's base set, so they are absent without any action.)
  pcall, xpcall and coroutine.resume are host wrappers (they latch memory errors that the script catches).
  string.rep is a host wrapper (the per-string cap). The originals are held by Rust only.

WHAT sandbox(true) DOES AND DOES NOT DO (tested)
  Does NOT remove any name: the 29 names left after our removals are all still there after sandbox(true) (F.sandbox-true-removes-nothing).
  Makes the library tables and the globals table read-only: `_G.x = 1`, `string.format = f`, `math.pi = 3`,
  `ctx.notify = nil`, `input.repo = 'x'`, `setmetatable(_G, {})`, `rawset(_G, ...)` all raise "attempt to modify a
  readonly table". getmetatable('').__index = {} also fails because the string metatable is read-only.
  Gives each run a writable thread-level globals table: a bare `leak = 'x'` succeeds in-run.
  In this design a fresh VM per run makes the cross-run question moot (A.tamper.between-runs: run 1 changes
  string.format, table.insert, ctx.notify, math.pi, string.rep, _G.leak, the string metatable and a bare global;
  every write is refused or confined; run 2 in a new VM sees the original values: "nil | nil | 7 | true | 3.141592653589793 | X | aa").

F. API FACTS (answers, with evidence in luau-extra and the F lines of the run files)
  1. Module format: runs as designed (F.module-format-runs: completed).
  2. M.meta without ctx and without host functions: yes. A VM with only the removals and the hook reads M.meta.name = "demo"
     with 1 step (F.meta-read-without-ctx). A module whose top level touches ctx fails with
     "workflow:2: attempt to index nil with 'name'" (ctx is an argument, not a global).
  3. Syntax errors: mlua returns Error::SyntaxError { message, incomplete_input }. With set_name("=workflow") the message is
     "workflow:3: Expected identifier when parsing expression, got '='" (chunk, line, message). Parse with
     ^([^:]+):(\d+): (.*)$. incomplete_input was false in all three cases tried. Missing "end": "workflow:4: Expected 'end'
     (to close 'function' at line 2), got 'return'". Unterminated string: "workflow:2: Malformed string; did you forget to finish it?"
     Without set_name the chunk is named after the Rust source file (not useful).
  4. Error values: a Luau error object is not preserved across the Rust call path. mlua turns it into RuntimeError with a
     string: error({code=7}) -> "table: 0x...\nstack traceback..."; error(nil) -> "nil ..."; error(42) -> "workflow:3: 42 ...".
     A Lua-side pcall preserves it: pcall(function() error({code=7}) end) -> type table, code 7 (luau-extra.jsonl).
     So ctx.try should be written in Luau (a small prelude using pcall), not in Rust. That prelude is NOT built or tested here.
  5. Listing ctx's names: yes. The host iterates the ctx table with pairs: "block_recv, count, notify, now, try".
     An unknown name can be reported with the list: a metatable __index on ctx (set before ctx is read-only) gives
     "unknown ctx function 'notfy'; valid names are: notify, now, count, block_recv, try" (F.unknown-ctx-name-message).
     A write to ctx stays "attempt to modify a readonly table". Not tested: whether getmetatable(ctx) then exposes that
     metatable to the script (it would hold only host functions, so no data should leak).
  6. Type stubs for editors: UNVERIFIED. luau0-src 0.18.3 has no Analysis directory (Ast, CodeGen, Common, Compiler, Config,
     Custom, Require, VM only), so mlua cannot type-check a script or a stub. I did not test Luau's declare syntax or luau-lsp.
  7. Luau version string: "Luau 0.709" (_VERSION).
  8. Recursion through pcall: the host's pcall wrapper gives a recursion depth of 99 (luau-extra.jsonl), while unwrapped
     Luau reaches 198 (F.pcall-recursion-depth.unwrapped, C-call limit 200). Cost of the wrapper: half the depth for
     pcall recursion. Benefit: the latch works for memory errors the script catches.
  9. The VM thread's interrupt fires at calls, returns and loop back-edges (VM_INTERRUPT in lvmexecute.cpp), so even
     "return" from execute is a point where a latched budget raises.

LATCHES AND CATCHING (the important one)
  Luau's interrupt error is catchable by pcall (tested: pcall returns false, the script continues to its next call).
  The host latches the budget reason at the first failure. Every later check (interrupt, ctx call, string.rep, ctx.try,
  block_recv) raises the same error again, and the run's outcome is the latched reason even if the script returned normally.
  Tested: "pcall(function() while true do end end); return 'caught without any call'" ends as budget:steps, because
  the function's return is itself an interrupt point. A script cannot make progress after a latch. The only code it can
  run is straight-line code with no call, loop or return, and it cannot return from execute, so it cannot finish.
  Memory: an allocation can fail with plenty of headroom left, for example a large table resize. So the interrupt's
  headroom check cannot see every memory error. pcall, xpcall and coroutine.resume are wrapped to latch when they
  return "not enough memory". The string.rep wrapper checks used + request > limit before calling the original, which
  is the allocator's own rule. mlua reports memory errors that cross a Rust call as RuntimeError("<nil>"), so
  is_memory_error() treats that text as a memory error too. Without these, the classification depended on timing
  (found and fixed during this run; the earlier numbers are discarded).

SURPRISES AND DESIGN NOTES
  - A budget error does not reach the script's result: the host reports the latch, not the script's return value.
  - Wall (2 s) and memory (64 MiB) are close. 64 MiB of 1 KiB strings takes 1.2-3.9 s here under load, so a legitimate
    memory-heavy workflow would hit the wall budget first. Consider a longer wall budget or a separate one.
  - Steps: 20M is about 20x a 1e6-iteration well-behaved loop (1,001,005 steps), and about 0.6-0.9 s of pure loop.
  - "String size" is only enforceable for library builders that the host wraps (string.rep here). Concatenation
    (..), table.concat and string.format are capped only by the total memory budget.
  - The print removal matters: Luau's print writes to the host's stdout, which is a side channel.
  - The interrupt hook costs roughly 11-33% on an interrupt-dense loop. mlua's own floor is about 5-7%.

NOT DONE, OR DONE WITH LIMITS
  - Type stubs and luau-lsp (F6): not tested.
  - Static C++ runtime: not achieved (E).
  - Linux only, one machine, shared with other workers. Tails are noisy.
  - Escape battery is not exhaustive. Reference-only checks were used where calling was unsafe.
  - The pcall wrapper's effect on recursion depth (99) is measured; the effect on the escape battery is not separately measured.
  - The budget values are starting points; they are not tuned.
  - The probe subcommand and the pcall-depth subcommand were added after the three full runs; they do not change the battery code.
